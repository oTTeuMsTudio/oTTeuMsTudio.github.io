Write a game engine based on Bevy

Bevy already owns the window, the GPU, and the tick. Your engine is plugins, components, and an editor on that World — same argument as oTTeCAD below, no garbage collector — then you push the crate to GitHub.

Open oTTeCAD Bevy.org The Reddit post

Posts like I’m working on a Rust game engine based on Bevy are not a rewrite of Bevy. Bevy is already a data-driven engine in Rust: an App, a World of entities, and DefaultPlugins for the window (winit), the GPU (wgpu), assets, and input. “Based on Bevy” means you stand on that. You write the opinionated layer — your components, your systems, your scene format, later an editor that inspects the same World.

You do not beat Unreal by starting here. You learn the loop Unreal already solved, with Bevy doing the metal: window, device, scene (ECS), tick, present. System-level Rust is the language for that loop. There is no garbage collector. Each entity, each component, each swapchain image has one owner. Bevy’s scheduler will not run two systems that both write the same component in the same frame — that is the borrow checker for the tick.

Bevy’s public source is the map: bevy.org · github.com/bevyengine/bevy. Copy the plugin cut. Name the crate yours. Then put it on GitHub so other people can cargo run --example hello it.

The systems you actually write

You do not start by writing an ECS. Bevy’s is the point of “based on Bevy.” You write plugins that register work on the schedule. A spinning cube with a camera is already an engine. The editor comes last — that is what makes a Reddit screenshot look like an engine, and it is also the part that takes years.

01 App and plugins App::new().add_plugins(DefaultPlugins). Window, input, GPU, assets. Your engine is more plugins on that App.
02 ECS Entity is an ID. Components are structs. Systems are functions. The World owns the rows — not a scene-graph of pointers.
03 Render Keep Bevy’s wgpu renderer until you have a reason not to. Custom materials and a render-graph node if you must.
04 Assets AssetServer, glTF, your scene format. One owner of the bytes. The GPU gets a copy the World also owns.
05 The schedule Startup, then Update. Input → gameplay → render. Parallel where queries do not alias. That order is the engine.
06 Editor, then GitHub Hierarchy, inspector, gizmos on the same World. Then a README, a license, and git push so the crate is a project, not a folder.

The World owns the frame

Memory is the argument, same as the modeler below. A C++ engine leaks when a node outlives its mesh. A garbage-collected engine pauses when the heap is walked mid-frame. Bevy makes the story compile: the World owns every entity. A Query<&mut Transform> is an exclusive borrow of that column. Two systems that both need it will not overlap. Drop frees the World — no GC scan.

That is slower to write than a high-level engine script. It is also why the frame can run next to the metal — native on the desktop, WebAssembly in a browser — without a runtime holding your hand.

Start with DefaultPlugins and a spinning cube. Your EnginePlugin next. Physics and an editor after the cube is yours. Some people later keep only bevy_ecs and write their own wgpu path. Do not begin there. Do not begin by forking the renderer.

Crate map

One crate until it hurts. Then a workspace so compile times and ownership stay honest. This is the Bevy-shaped cut: a facade plugin, your data, extra render only if you need it, editor last. 

my-engine/
  Cargo.toml                 # [workspace] members; pin bevy = "0.19"
  crates/
    engine/                  # facade — DefaultPlugins + EnginePlugin
    core/                    # your components, resources, events
    render/                  # extra passes / materials — optional
    editor/                  # hierarchy, inspector, gizmos — last
  examples/
    hello.rs                 # spinning cube. cargo run --example hello
  README.md
  LICENSE                    # MIT OR Apache-2.0, like Bevy
  .gitignore                 # /target, *.pdb

Push it to GitHub

A crate that only lives on your disk is a sketch. GitHub is how it becomes a project other people can clone, compile, and fork. Install Rust from rustup.rs so cargo --version prints. Install GitHub CLI if you want gh repo create in one step.

  1. Scaffold: cargo new my-engine --lib. Add bevy = "0.19" in Cargo.toml. On Windows, bevy = { version = "0.19", features = ["dynamic_linking"] } in the example crate keeps iteration faster. Split into the workspace above when the first module is no longer a sketch.
  2. Keep build junk out of git. Cargo already writes a .gitignore with /target. Add *.pdb on Windows.
  3. Write README.md — what it is, how to cargo run --example hello, which Bevy version you pin, what GPU it needs. Add LICENSE. MIT OR Apache-2.0 is the Rust default, and Bevy’s.
  4. Commit locally, then publish. gh creates the empty repo and pushes in one command. Without it, create the repo on github.com and add the remote yourself.

Optional next: a GitHub Action that runs cargo test on every push. Optional later: compile a wasm demo with --target wasm32-unknown-unknown and park it on GitHub Pages — the same way oTTeCAD sits on this site. The modeler below is that discipline applied to mesh topology instead of an ECS World.

Writing my own 3D modeler

I am building oTTeCAD in Rust system-level code — mesh topology, GPU viewport, tools, and undo I own. Not a plugin, and not a script on top of someone else's editor. The same workbench compiles to WebAssembly and runs here.

This is the hard path. System-level Rust sits next to C and C++: you talk to the GPU, lay out bytes, and keep a mesh alive without a runtime holding your hand. There is no garbage collector. If a vertex buffer, an undo stack, or a selection set is allocated, I own it until it is dropped. The borrow checker will not compile until that story is true — no dangling pointers, no use-after-free, no two writers on the same memory.

Memory management is the argument of the language. Each value has one owner. Other code may borrow it for a limited time. Lifetimes are the compiler proving those borrows do not outlive the owner. That is slower to write than Python, JavaScript, or a high-level engine script. It is also why this editor can run next to the metal — native on the desktop, WebAssembly here — without leaking, and without a GC pause walking the heap.

oTTeCAD is a desktop modeler. Open this page on a computer with WebGPU or WebGL2 (Chrome, Edge, or recent Firefox).
